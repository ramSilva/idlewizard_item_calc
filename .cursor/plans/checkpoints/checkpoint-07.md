**BiS bot algorithm** (https://idle-wizard.fandom.com/wiki/BiS_Guide, "How it Works" / "Formula Generation"):
- Builds a postfix formula by substituting effects, multiplicative before additive, and drops items that don't affect it.
- Per enchant level, scores each item "best case", treating every set effect as belonging to that item alone, and keeps items per slot until the first non-set item (2 for rings).
- Tests every subset of each set against the non-set alternatives, then every remaining combination.
- Runs at least 40 levels and stops after 15 unchanged levels once the second-best set grows more slowly than the best. Resonator is handled as a separate branch.
- Defaults: attributes 175, max paragon (all slots). Pro=SubParagonN excludes slots: 12 Shoulder/Waist, 18 Neck/Rings, 24 Back/Wrist, 28 Weapon.
- Weapons are flagged as unreliable because their effects are self-scaling.

### Unverified item assumptions (each carries a note in the data; the UI's Results tab lists the ones behind each result)
1. Percentage item bonuses multiply ×(1+N%) (and percentage perks without "(additive)").
2. **"(base)" adds to the stat's base value.** Biggest risk: `Mysteries.Power` base is 0.03, so Circlet Of Deep Thoughts' "(base) +20%" adds 0.20 (≈ 7.7× Mysteries power alone). Validate against the Temporalist guide's enchant/stat tables or presets (golden tests) before trusting Mysteries-power items. Same reading for "Void Mana profit (base) +N%".
3. Set tiers cumulative.
4. Slot-/self-scoped bonus enchant levels are not capped at 5 (evidence: Raiments offers +8).
5. Phylacteries: "scales multiplicatively from Character level" = factor^level; "decreases X +N%" = (1 − N%)^level. **The optimizer results make this look suspicious** (section 9: Robust Tangerine / Inert Jade Phylactery contribute ×1e10–×1e23 at character level 1000–2000; the UI shows Inert Jade at ×2.05e21 for Shaman at enchant 0).
6. Formula values as fractions ×(1 + value) (Cage, Hunger, Murmuring, Accelerator, Black Vortex, Collar, Symbol); "X by (formula)" = ×formula (Miniaturized Accelerator, Enigmatic Parchment — Miniaturized is < 1 for small shard counts); formulas with their own "+ 1" are the factor (Memento, Paukan, Habitstone).
7. Weapon abilities active during the burst (Thunderbird, Black Blade, Shard Of A Lost Dimension, Cataclysm); Reality Prism charges at maximum `B^(2R)·10 + 1`; Head Of The All-Eater's "log10^2" = squared log and the "accrued" period is unclear.
8. Recaller Stone's "Autoclicks" = autoclicks this Exile; Arcane/Miniaturized Accelerator's catalyst shards are one input.
9. Conjured Razorspaulders "Pet ability power +100" (no %) added to the PAP base as written. **Also suspicious in the optimizer results**: it's in every class's best set (×8e3–×3.5e6), against the PAP base placeholder 1.
10. Spirit's Guidance Legendary's trailing "150%" applies to critical rating.
11. Mutated Mycelium Rare: factor 0.021 vs "(2.7% per Expedition Level)"; the factor is used.
12. Item attribute bonuses count as points for per-point bonuses (thresholds: supported by the Temporalist guide); Int 150's "trained" points = assigned points.
13. Cost reductions add up; crit chance items add percentage points; "Entities" = Void entities; flat pet XP and flat VM/entity combine in undocumented ways (own stats).
14. Units: `Pet.TimeCurrent` seconds (game time incl. skipped); Void entity spawn rate and passive shard generation units unknown.

### Model builder (`src/data/buildModel.ts`)
- `buildModel(selection, { relevance? = true }) → BuiltModel`; `ModelSelection { classId, petId, spells (≤ 6, must be class spells), stance?, idle? (default true), snapped? (default class's, only applies to selected spells), scoreId? (default class's) }`; `defaultSelection(classId)`; `MAX_SPELLS`; `itemCatalog()` (cached `ItemCatalog(ITEMS, SETS)`). Throws if the score isn't available for the selection ("Score X isn't available for this selection (available: …)").
- Assembly: generic stats + active spells' stats (selected ∪ class augments; snapped spells get their refs substituted) + pet stats + `Pet.Tier` constant + builder-derived stats (`Spell.ActiveSummons`, `Click.SpellAutoclicksPerSecond`, `Click.AutoclickManaPerSecond`, `Spell.<Key>.ManaPerCast/ManaPerSecond`, `Pet.CastManaPerSecond`, `Void.ManaPerSecond`) + class stats (replace). - Helpers: `loadoutModifiers(model, equipped, legion)` (`[]` = no items); `elasticity(model, statId, baseMods, inputs?, step = 0.01)` = d ln(score)/d ln(stat) by central difference on the stat's item log-multiplier (throws for stats without item multipliers, e.g. `Hero.AbilityPowerGrowth`, `Char.Level`).

### How to add things

## 8. Engine APIs from earlier steps (unchanged)

### `src/engine/expr.ts`
Expr AST `num | ref | bin(+ - * / ^) | neg | fn`. `f(source, bindings)` parses infix: dotted identifiers are stat ids, single letters (or any undotted name) must be bound (`{ P: "Pet.AbilityPower" }` or to an Expr). `^` is right-associative and binds tighter than unary minus (`-2^2 = -4`; write `x ^ (-1)`). Functions: `log10 ln log(base,x) max min sqrt ge lt if(c,a,b) floor abs` (no equality; round = `floor(x + 0.5)`). Helpers: `num ref bin mul add pow call(fn, ...args)`, `refsOf`, `toInfix`, `toPostfix`. Avoid negative bases with `^` (use `max(…, 0)`).

### `src/engine/stats.ts`
`inputStat(id, label, group, spec, extras)`, `multiplierStat`, `additiveStat`, `constantStat`, `derivedStat`. `StatRegistry`: `add` (rejects duplicates, bad ids, input+base), `extend`, `withInputDefaults({id: value})`, `has/get/require/all`. `createGenericRegistry()` in `src/data/stats.ts`. `InputSpec { default, kind: number|integer|boolean, min?, max?, logScale?, unit?, hint? }`.

### `src/engine/graph.ts`
- `compileGraph(spec)` (throws `GraphError { issues }`), `tryCompileGraph`. `GraphSpec = { stats, effects?, score, items?: ItemEffectSpec }`. Only stats reachable from the score are compiled. Issues: `unknown-ref`, `unknown-target`, `cycle`, `missing-input`. `StatGraph`: `stats` (`CompiledStat { id, index, def, base: {kind: input, spec} | const | expr, … }`), `index`, `score`, `inputs` (indices of input stats), `dynamic`, `inertItemStats`. Helpers `statIndex`, `exprItemDependent`, `exprInputs`.
- `ItemModifiers = { add, logMul, dynamic }`; `createModifiers(graph, { add?, mul?, dynamic? })`. A stat's value is `(base + Σadd effects + add[i] + Σ active dynamic adds) × Π mul effects × 10^logMul[i] × Π active dynamic muls`.
- `FloatEvaluator(graph, inputs?, options?)` (signed log10 arithmetic; item-independent stats cached): `scoreLog10(mods?)`, `evaluate(mods?)`, `statLog10(id)`/`statSign(id)`, `setInputs`/`setInput`, `inputValues()`. Options: `activeItems` (cache stats depending only on inactive item coordinates), `incremental: true`. `InputValues = Record<id, number | Decimal | boolean>`. Decimal fallback `evaluateDecimal`, `resultToDecimal`. Speed on class models: ~60–95k evaluations/s plain.

### `src/engine/relevance.ts`
`analyzeRelevance(graph, { inputs?, candidates?, epsilon?, reference?, threshold? })` → `{ inputs: InputRelevance[] (id, label, group, shown, method, reason, maxDeviation?), terms }`. Structural log-decomposition plus numeric ratio invariance over sampled input values (`sampleValues`). `reference` (candidates are compared with this set instead of no items) and `threshold` (log10; deviations up to it are hidden with a "below the noise threshold" reason; default 0). `syntheticCandidates(graph)` probes each item stat alone and "everything on". Limitations: a whole-score exponent input is shown although it can't change the order; the numeric check holds other inputs at current values; inputs consumed by the modifier builder (`Items.LegionReward`, enchant levels) never appear in the graph; **attribute points also gate item requirements, which the ratio check can't see** (the UI forces them visible, section 10).

## 9. Optimizer (plan todo `optimizer`: done; unchanged in this step)

### Core (`src/engine/optimizer.ts`)
- `new Optimizer(problem, options)`; `problem: OptimizerProblem { graph, catalog, items, sets, inputs?, attributes? }` (attributes default to the graph's `AttrPoints.*` inputs). Methods: `optimizeLevel(level, previous?) → LevelResult` (previous warm-starts and sets `changed`), `sweep(levels = ENCHANT_LEVELS, onLevel?) → SweepResult`, `sweepResult(rows)`, `scoreOf(keys, level)` (exact log10; -Infinity if a requirement is unmet; keys must be in the pool), `modifiersFor(keys, level)`, `relevance(row, { threshold = DEFAULT_NOISE_THRESHOLD (log10 1.01), maxCandidates = 40 })`. Fields: `excluded: ExcludedItem[] { key, name, reason: not-owned | mythic | excluded-slot | requirements | no-effect | resonator-disabled }`, `baselineLog10` (no items), `legion`. Helpers `optimize(problem, options)` (one level, `options.enchant`), `enchantSweep`, `ENCHANT_LEVELS` (0..55).
- `OptimizerOptions`: `owned?: Record<itemKey, Quality>` (default every non-Mythic at max quality; given explicitly, Mythics are allowed — the UI always passes it explicitly), `excludedSlots`, `enchant` (for `optimize`), `enchantOverrides: Record<itemKey, level>` (fixed across the sweep), `legion`, `resonator` (default true; false drops "all"-scope bonus items), `pruning: "bot" | "none"`, `marginalTolerance` (log10, default log10 1.05), `runnersUp` (default 0), `polishDepth` (default 0), `nodeBudget` (default 200 000).
- Results: `LevelResult { level, best: SetResult, branches: SetResult[], changed }`; `SetResult { items: ChosenItem[], scoreLog10, gainLog10 (vs no items), forced (Resonator key or []), candidates (keys the exact search chose from), stats: SearchStats }`; `ChosenItem { key, name, slot, quality, set, enchant (real), effectiveEnchant, contributionLog10 }` — contribution = log10(score with / score with that slot empty), **Infinity when removing it breaks another item's requirement** (the UI shows "required"); `SearchStats { candidates, positions, leaves, bounds, evaluations, exhaustive, complete, ms }`; `SweepResult { baselineLog10, excluded, levels, changes }` (`changes` = levels where the best set differs from the previous level, like the bot's "Enchant N" rows). All results are plain data (structured-clone safe; JSON needs Infinity handling).
- Semantics: real enchant = override ?? global level, clamped 0..55, and 0 unless the item is Legendary/Unique and its enchant stat reaches the score. Effective level as in `resolveLoadout` (leaves are exact; tested against `resolveLoadout` + `modifierSpec`). Requirements checked at every evaluation (item attribute bonuses and reached set tiers count, own bonus excluded), pre-filtered optimistically (assigned + best possible bonuses of other candidates).
- Pipeline per level and branch: (1) pool filter + structural "no effect"; (2) standalone best-case gain with the item's whole set counted (requirements ignored), bot rule per slot ("until the first non-set item", 2 for Finger/Trophy); greedy coordinate ascent over the whole pool from the previous level's set or the standalone ranking (≤ 6 passes), recording each item's best score in its slot ("marginal"); finalists = greedy items ∪ items within `marginalTolerance` of the greedy score ∪ top `runnersUp` ∪ bot keeps whose set wins the subset test; (3) set-subset test: every subset (≤ 10 pieces) of each kept set against the best non-set alternatives; the best configuration seeds the search; exact dominance pruning among non-set finalists; (4) exact search; then a 1-swap polish over the whole pool (and the optional pair polish), feeding improvements back into the finalists (≤ 3 extra rounds); (5) branches: Resonator excluded and Resonator forced (one branch per "all"-scope item; Finger capacity drops by one); slot bonuses (Power Armor, Raiments, Burden) are applied exactly at leaves; (6) contributions and effective levels of the best set of each branch.
- Exact search: positions = open slot positions (Finger/Trophy as one position with pairs), options = finalists (+ empty). Positions whose finalists always help are fixed. **Optimistic bound** = score at working modifiers + per-coordinate favourable extremes of the remaining positions + favourable parts of each set's tiers up to its reachable piece count + favourable bonus-level extras. **Directions** (per coordinate: up, down or ambiguous) are measured once per optimizer by finite steps at no items, all candidates on, and all candidates at max enchant; ambiguous coordinates disable the bound where they're touched. The bound is only valid if the score is monotone in each coordinate in that direction everywhere (not proven; checked by the brute-force tests). Positions are ordered by how much each loosens the bound at the seed. ≤ 2048 leaves → plain enumeration. Budget exceeded → `complete: false` and a pairwise local search over the positions.
- Relevance with real candidates: reference = the level's best set; candidates = both branch bests, the best single-item swap of every slot, then the best swaps up to 40, all from the whole pool. At the guide levels this shows Oni 18 of 67 inputs (build-time relevance: 48), Shaman 25 of 66, Temporalist 27 of 73. Shown examples: Oni `Weapon.CataclysmCharges`, `Pet.Level`, attribute points, `Spell.IronBlood/RitualOfPower/EnhancedStrength.CastsThisExile`, `Building.6.Count`; Shaman `Weapon.BranchCharges`, `Hero.AbilityPower`, `Misc.CatalystShards`, `Click.CritChance`; Temporalist `Spell.QuasiIncantation.CastsThisExile`, `Pet.AbilityPower`, `Building.8.Count`, and `Building.1–7.Share`. `Idle.Active` shows everywhere (the UI treats it as the Setup toggle).

### Known limitations of the optimizer
1. The default pruning is a heuristic (like the bot's); only `pruning: "none"` is exhaustive over the owned items, and that's only practical for small catalogues. Even "none" relies on the monotonicity the bound assumes; directions come from three sample points.
2. The per-coordinate bound is loose (at Oni 17 the root bound is ~42 log10 units above the optimum), so the exact search only stays small because the finalists are few. Adding runners-up makes it explode.
3. Requirement enablers are only found if the greedy/marginal ranking picks them up; the standalone ranking ignores requirements.
4. Cancellation in the worker takes effect between levels (a level takes ≤ ~1 s at default inputs); `terminate()` stops at once.
5. The optimizer uses one set of inputs for all levels; per-item quality comes from `owned`. Mythics are only searched if listed in `owned` (inherent effects only).
6. The "changed" flag compares item keys only (not quality/enchant).
7. `relevance()` evaluates ~40 candidate sets × all inputs × ~8 sample values (≈0.3–0.5 s); `Idle.Active` always shows.

### State / URL format
`#s=<base64url(JSON)>`, same string in localStorage. JSON keys, only those differing from `defaultState(c)`: `c` class id (always), `p` pet, `s` spells, `t` stance (`""` = none), `d` idle (0/1), `n` snapped, `o` score id, `i` inputs (typed strings; entries equal to the default dropped when the model's specs are known), `e` global enchant, `v` overrides `{itemKey: level}`, `q` owned differences `{itemKey: index into QUALITIES, -1 = not owned}`, `x` excluded slots (indices into `ITEM_SLOTS`), `r` Resonator allowed, `l` Legion, `w` full sweep. A default state encodes as `{"c":"oni"}`. Decoding sanitizes everything (unknown class → Oni defaults; unknown pets/items/qualities/slots dropped; non-class spells dropped; enchant clamped 0–55; snapped limited to selected snappable spells); unreadable strings give the defaults. Scores are validated at build time (fallback + warning). If ITEM_SLOTS or QUALITIES order ever changes, bump the format (indices are stored).

### Known UI limitations / open problems
1. The page bundle (~690 kB, 167 kB gzip) includes the whole data layer because the model is built on the main thread for the form; fine for Pages, but could move `buildUiModel` into the worker later.
2. The quick run re-optimizes the global level on every change (debounced 500 ms, ~1–2 s at defaults). Extreme inputs (e.g. 1e12 for CAP growth or character level) make runs much slower and can exhaust the search budget (flagged in Results).
3. Relevance is computed at the global enchant level only; an input hidden there could matter at another level of a sweep.
4. The BiS bot SubParagon buttons use the bot's numbering and a cumulative reading (assumption); the "My Paragon level" control uses the wiki's Paragon table.
5. Changing class resets inputs (defaults are class-specific); items/owned/overrides persist across classes.
6. No explicit "compare with guide preset" in the UI (the CLI has `--preset`); could be added in `validate`.
